## Per-model autotuner 2026-11-13 (manager; 1003 Rust + 185 UI tests, fmt/clippy -D warnings/tsc/build clean; run live on the RX 9060 XT)
- [x] "Optimize speed" on every installed model (Models > Library): confirms first, then runs `llama-bench` from the selected runtime (`raptor_runtime::tune`, `AppState::tune_model`) at the recommended GPU layer count and, only where the oversubscription rule applies (sparse MoE larger than VRAM), at all layers, each across micro-batch 256/512/1024 (prompt 2048, reply 64, one model load per layer count). The winner is the setting with the least time for a representative request (4096-token prompt + 256-token reply), which weighs prompt and generation speed the way an agent session does. Refused while a model is loaded (it needs the GPU); a layer count that fails (e.g. out of memory) is reported and skipped; nothing is saved if nothing could be measured.
- [x] Saved to `config/tuned.json`, keyed by machine fingerprint + model content hash + runtime id + runtime version, so a new runtime build, GPU or file is measured again. A corrupt file is treated as empty. Every later load applies it (layers, micro-batch), notes it in the load rationale ("Tuned on this machine: ... N% faster than the untuned setup"), and keeps the untuned speed plan as the fallback if the tuned setup cannot start. "Forget this tuning" removes it.
- [x] Live result, Ornith-1.5-35B-A3B in the real app: 136 s; best 41 layers at micro-batch 256 (prompt 2,215 tok/s, generation 67.3 tok/s) vs the untuned 39 layers at 512 (1,790 / 48.2): 34% less time for a long prompt plus a reply. Table: ngl 39 ub 256/512/1024 = 8.4/7.6/10.8 s; ngl 41 ub 256/512/1024 = 5.7/8.5/8.9 s. The next normal load used it (verified 41/41, notes list the tuning and n-gram speculation) and ran 76.5 -> 92 tok/s over the API.
